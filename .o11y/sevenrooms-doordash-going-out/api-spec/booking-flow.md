# SevenRooms / DoorDash Going Out Discovery + Booking Flow

## What was created

This artifact extends the Browserbase `browser-to-api` output with a safety-scoped booking-flow map.

Generated by `browser-to-api` from the trace:

- `openapi.yaml` / `openapi.json` — observed API spec
- `client.mjs` — generated zero-dependency client for observed endpoints
- `report.md` / `index.html` — coverage reports
- `confidence.json` — per-endpoint confidence

Additional files added for the reservation flow:

- `static-js-endpoints.md` / `static-js-endpoints.json` — endpoint strings extracted from public SevenRooms widget JS
- `booking-flow-overlay.openapi.yaml` — overlay spec with live-observed and static-observed boundaries

## Trace scope

Live HTTP calls were intentionally limited to low-frequency, non-mutating requests:

1. `GET /api-yoa/availability/widget/range` for `armaniristorante`, party size 2, 3-day range.
2. `GET /api-yoa/availability/widget/range` for `armaniristorante`, party size 4, 3-day range.
3. `GET /api-yoa/availability/widget/range` for `negrilbk`, party size 2, empty-availability sample.
4. `GET /api-yoa/venue/reservation_widget_settings_v2` unauthenticated boundary probe; returned `401`.
5. `GET /api-yoa/dining/venue_info` malformed/insufficient-context probe; returned `400`.

No booking hold, payment session, reservation creation, cancellation, or DoorDash marketplace mutation was called.

## Discovery flow

```text
restaurant/marketplace UI
  -> GET /api-yoa/availability/widget/range
       query: venue, time_slot, party_size, halo_size_interval, start_date, num_days, channel=SEVENROOMS_WIDGET
       response: date -> shift -> times[]
       important slot fields:
         time_iso
         utc_datetime
         access_persistent_id
         access_rule_id
         shift_persistent_id
         experience_id
         require_credit_card
         cancellation_policy
         pacing_covers_remaining
```

The successful trace confirms that the availability endpoint can return bookable slot metadata and policy/payment hints. It does **not** prove that a caller can book; it only identifies candidate slots and the downstream identifiers a first-party checkout flow would likely use.

## Booking-flow boundary

Static SevenRooms widget JS exposed likely downstream flow clues:

```text
GET availability/range
  -> POST /api-yoa/dining/hold/add              # probable hold table step; not called
  -> POST /api-yoa/dining/hold/upgrades         # optional upsells; not called
  -> /api-yoa/customer-payment-session/         # payment setup clue; not called
  -> /api-yoa/customer-adyen-session/           # payment setup clue; not called
  -> privileged reservation/guest/payment paths # not enumerated by live trace
```

Because those downstream paths are write/payment-sensitive, they remain `static-observed only` in the overlay spec. Treat them as a map of where a first-party browser flow probably goes, not as a public API contract.

## DoorDash Going Out boundary

The public SevenRooms widget JS also contains `/api-yoa/doordash_marketplace*` and `/api-yoa/doordash_storefront*` strings. In this trace, those were **not** exercised and appear more like SevenRooms partner/admin configuration surfaces than consumer-facing DoorDash Going Out booking APIs.

Current evidence still supports the labs-wiki conclusion:

- public discovery is observable through SevenRooms widget availability;
- booking mutations likely require first-party widget state, CSRF/session context, payment handling, and/or partner-approved DoorDash/SevenRooms credentials;
- DoorDash Going Out consumer booking operations were not found in public DoorDash web specs or this live SevenRooms trace.

## Safe next capture, if needed

To improve the booking spec without creating a real reservation:

1. Use an owned browser/account context only if authorized.
2. Enable request/response body capture.
3. Walk the UI only until a table is held or checkout form is shown.
4. Stop before final submit/payment/reservation confirmation.
5. Redact cookies, CSRF tokens, contact info, payment fields, and any guest identifiers.
6. Re-run `browser-to-api` on that richer trace.
