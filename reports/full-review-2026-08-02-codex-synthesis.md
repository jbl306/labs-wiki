# Labs Wiki comprehensive review: Codex migration and synthesis quality

**Date:** 2026-08-02
**Scope:** repository, live homelab runtime, raw-source lifecycle, Codex integration,
synthesis corpus, knowledge graph, lint/evaluation, cost/privacy/reliability, and
prior review follow-through.

## Executive assessment

Labs Wiki has a strong core architecture—immutable raw capture, provenance-first
wiki pages, deterministic extraction seams, a graph/MCP layer, and a testable
Python control plane—but it is currently **operationally split across two eras**:

- the repository has a Codex backend;
- the live `wiki-auto-ingest` container still runs Copilot CLI;
- the session source feeder still watches Copilot checkpoint files;
- most of the corpus and all synthesis pages predate a claim-level evidence
  contract.

The most important conclusion is that changing the model alone will not improve
synthesis. The system needs a better **selection → evidence packet → composition
→ deterministic evaluation → controlled finalization** loop. This review
implements deterministic checkpoint preflight, prompt-level selection, bounded
composition, evaluation, manifest-scoped commits, and safer finalization. The
remaining architectural step is to make Codex return a typed proposal to a
backend-neutral renderer instead of letting it write pages before validation.
Deployment and Codex-session capture remain explicit P0 follow-up work because
live service changes and OAuth secret placement were not applied during this
review.

## Prioritized findings

### P0 — The Codex migration is implemented but not deployed

**Evidence**

- Repository default: `WIKI_INGEST_BACKEND=codex-cli`.
- Live container: `WIKI_INGEST_BACKEND=copilot-cli`, model `gpt-5.4`.
- Live image contains `gh` but no `codex` binary.
- The July pending source failed specifically because Copilot access is no longer
  available.

**Impact**

Auto-ingest is not currently reliable. No prompt or synthesis improvement in the
repository affects the live service until a new image, a dedicated writable
Codex auth directory, and compose configuration are deployed.

**Recommended deployment boundary**

1. Build the reviewed `Dockerfile.auto-ingest` with its pinned Codex version.
2. Create a dedicated, mode-0700 Codex home for this service and mount only the
   existing mode-0600 subscription `auth.json` into it read-write; do not copy,
   print, or commit the credential.
3. Set `WIKI_INGEST_BACKEND=codex-cli` and an explicit model in compose; remove
   Copilot-only environment and mounts from this service.
4. Add a local watcher-process health check and make `codex login status` a
   fail-closed deployment verification rather than a recurring network health probe.
5. Recreate only `wiki-auto-ingest`; its startup scan will retry the pending July
   source.
6. Verify the created source page, raw status, log entry, synthesis audit, and
   graph/index rebuild before considering migration complete.

No live compose edit, auth copy, container rebuild, or restart was performed in
this review.

### P0 — Session capture is still Copilot-specific

**Evidence**

- 67.9% of raw files came from `copilot-session-curator`.
- The active systemd watcher path is the Copilot checkpoint directory.
- Codex writes sessions under `~/.codex/sessions`; those files are not promoted.

**Recommendation**

Replace the single-format curator with an **agent-session curator** having parser
adapters. For Codex, extract only user messages, final assistant messages,
compaction summaries, and file-change metadata after an idle/closed-session
boundary. Do not ingest raw reasoning/tool-event JSONL wholesale: it can contain
secrets, massive logs, and low-signal execution chatter. Deduplicate exports by
`session_id + last_event_timestamp + content_hash`, then pass the durable summary
through the existing checkpoint classifier.

This is more important for future synthesis quality than backfilling another
batch of old pages: synthesis cannot connect knowledge that never enters the
corpus.

### P1 — Synthesis selection was volume-oriented

The old prompt effectively treated “two concepts found” as sufficient reason to
create synthesis. That makes synthesis an ingest side effect rather than a
separate editorial judgment. It also encourages same-session comparisons and
mechanism-shaped titles.

The prompt now requires a defensible decision, trade-off, recurring pattern,
mechanism, or contradiction; a targeted evidence packet of 2–6 pages; an
existing-page search; explicit within- vs cross-source scope; and at most one
new synthesis per ingest.

The next architectural step should be a weekly **report-only synthesis candidate
queue** driven by:

- graph cross-community surprise edges;
- unresolved contradictions;
- frequently co-retrieved concepts;
- high-degree concepts lacking synthesis coverage;
- evidence-family diversity.

Candidate selection should be independent of whichever raw happened to arrive
most recently. Codex can then curate a small batch from bounded evidence packets.

### P1 — Provenance existed, but claim-level evidence did not

A page-level `sources:` list says where the page came from, but not which source
supports which insight. New synthesis pages now require:

```yaml
evidence_scope: cross-source       # or within-source
evidence_source_count: 2
```

and an `## Evidence Map` with columns for Insight, Supporting pages, Raw
provenance, and Confidence/limits. This makes conflict and weak-evidence review
possible without another model call.

### P0 — Codex still uses a write-first architecture

The agent-CLI branch still asks Codex to search, deduplicate, edit, and synthesize
inside a writable checkout. It now has deterministic checkpoint `skip` and
planning-only preflight, schema-constrained reporting, a pre/post checkout
manifest, path/provenance validation, a synthesis gate, validation-run isolation,
and path-limited `git commit --only` finalization. Those controls prevent false finalization and reject
unreported writes, but they do not roll back files written before a timeout or
failed audit, and the full deterministic legacy merge renderer remains bypassed.

The durable target should be backend-neutral orchestration: Python classifies the
source, selects canonical candidates, builds the bounded evidence packet, and
hands Codex a read-only extraction/synthesis task. Codex returns a typed proposal;
Python validates, renders, deduplicates, and publishes it. This is a larger
refactor and remains the highest-value architecture item after the live migration.

### P1 — Checkpoint cluster identity and evidence breadth were unsafe

The checkpoint backfill previously treated graph community numbers as persistent
IDs, although greedy-modularity community numbers are positional and can change
between builds. It could therefore attach a changed cluster to an unrelated old
synthesis. It also passed at most four page bodies to the model but listed every
raw checkpoint in the cluster as evidence, and two log call sites could throw
`KeyError: agent` after page writes.

The reviewed implementation now:

- matches existing cluster synthesis only by a versioned hash of sorted raw IDs or
  an exact source set—never by community number alone;
- prevents one existing page from satisfying two clusters in one run;
- records only raw provenance from the actual bounded model input pages;
- maps each generated insight only to provenance from its named supporting pages
  and rejects generated pages that fail the strict synthesis audit;
- records the evidence-input count separately from broader cluster membership;
- truncates generated titles at word boundaries; and
- supplies explicit agent identifiers at every shared log call site.

A final dry run found five changed clusters needing new/editorial synthesis and
one exact-source-set match. It no longer silently reused pages by stale community
number.

### P1 — Codex output was not machine-enforced

The integration previously requested JSON in prose, parsed any embedded object,
and converted missing JSON into partial success. The agent was also instructed
to mutate raw status and `wiki/log.md` itself. That could produce a false
successful transaction even when the Python caller could not validate the
result.

The reviewed path now:

1. computes checkpoint retention before invoking an agent and blocks planning-only
   promotion into canonical concepts/synthesis;
2. calls `codex exec --output-schema`;
3. uses `--ephemeral` to avoid session-rollout accumulation;
4. uses `--ignore-user-config` so unrelated MCP/plugin configuration does not
   enter unattended runs (authentication still uses `CODEX_HOME`);
5. treats malformed/missing status as failure;
6. validates every decoded backend result against the same JSON Schema, validates
   created and updated paths, rejects unreported checkout changes,
   validates source-page provenance, and runs the strict synthesis audit;
7. requires normalized in-repository `raw/*.md` provenance, exact supporting-page
   agreement between each Key Insight and Evidence Map row, existing supporting
   wiki pages, and provenance that belongs to each named supporting page;
8. rebuilds the deterministic index before success log/status/notification
   finalization and leaves raw status pending when that gate fails;
9. keeps validation runs out of the log, notification, and commit paths; and
10. gives log/status finalization and path-limited git staging/commit exclusively to
   the Python orchestrator.

This follows OpenAI's current non-interactive guidance for explicit sandboxing,
structured outputs, and automation auth.

### P1 — Evaluation did not target synthesis quality

The new `scripts/audit_synthesis.py` provides deterministic page and corpus
metrics for provenance existence, evidence scope, source-family diversity,
required sections, Key Insight grounding, Evidence Map coverage, comparative
depth, and title quality. It can gate one new page in strict mode or emit a JSON
corpus report.

This is necessary but not sufficient. A proper model/prompt evaluation set should
add 10–20 frozen source bundles with:

- expected “do not synthesize” cases;
- within-source and cross-source cases;
- conflicting-source cases;
- near-duplicate existing synthesis;
- expected decision/trade-off statements;
- pairwise human preference against the current production output.

Use the deterministic audit as a hard gate and human/LLM-judge scoring only for
novelty, usefulness, and epistemic calibration. Keep the judge blind to model
identity and periodically check judge/human agreement.

### P2 — Consolidation policy is defined but not operating

Ninety percent of pages remain `hot`, 866 are stale, and only two are
`established`. Staleness should not trigger blind `last_verified` updates. Run
maintenance by graph importance and source volatility:

1. verify high-degree operational/entity pages first;
2. promote durable, multi-source pages;
3. archive low-signal checkpoint material;
4. merge or retitle the six recurring-checkpoint synthesis artifacts;
5. preserve redirects/aliases so wikilinks do not break.

### P2 — Graph quality is good enough to guide work, not judge it

With 3,304 edges and one orphan, the graph is a strong retrieval substrate. But
centrality currently rewards ingestion artifacts, and TF-IDF similarity is
lexical. Use graph signals to propose evidence packets, then require the strict
synthesis contract and editorial review. Do not auto-create synthesis solely
from degree/community scores.

### P2 — Deployment/repository drift needs one owner

The runtime bind mounts only selected directories, so its internal git-commit
setting cannot work. The host generates periodic snapshot commits and is 59
commits ahead of the remote. Decide explicitly whether:

- the host owns periodic commit/push and the container never commits; or
- the container gets a controlled worktree and deploy key.

The first option is simpler and safer for this homelab.

## Codex subscription, cost, privacy, and maintenance trade-offs

### Cost

OpenAI's Codex README states that ChatGPT-managed Codex is included with Plus,
Pro, Business, Edu, and Enterprise plans. ChatGPT-managed auth avoids a separate
per-token API bill, but usage is still subject to plan/rate limits. API-key auth
is separately metered and is not the low-cost default for this workload.

A real local structured-output smoke succeeded with the current ChatGPT login and
used 22,062 total tokens for even a tiny request, largely because Codex loads its
agent context. `--ignore-user-config`, bounded 2–6 page evidence packets, source-
aware reasoning effort, and a one-synthesis cap are therefore important quota
controls.

### Authentication and reliability

OpenAI documents ChatGPT-managed auth in unattended CI/CD as an advanced path and
says to treat `~/.codex/auth.json` like a password. The file must be securely
seeded, writable for refresh, and persisted between runs. A dedicated service
`CODEX_HOME` is preferable to mounting the user's complete `~/.codex`, especially
because the host config contains unrelated MCP servers and model preferences.

The Docker image previously installed `@openai/codex@latest`, creating an
unreviewed breaking-change path. It now pins 0.145.0; upgrades should be explicit
and verified with the structured-output smoke and container tests.

### Privacy and source rights

Codex processing sends selected raw/wiki content to OpenAI; the prior Copilot
path sent it to GitHub's model service. This is not a self-hosted inference path.
Add a frontmatter policy such as `sensitivity: local-only | cloud-ok` before
capturing private credentials, health, legal, or other sensitive notes. A
`local-only` source should use deterministic extraction plus a local model or
remain raw-only.

Raw web snapshots also remain subject to source terms and copyright. Preserve
URL/provenance, store only what is needed for personal indexing, and avoid
republishing full copyrighted bodies from this repository.

## Changes implemented in this review

- Added `scripts/audit_synthesis.py` with strict page gating and corpus JSON
  reporting.
- Added synthesis frontmatter/evidence-map requirements to the ingest prompt and
  project instructions.
- Replaced the “two concepts ⇒ synthesis” rule with an editorial value gate and
  targeted evidence packet.
- Reduced the default synthesis cap from two to one per ingest.
- Added Codex JSON Schema output, ephemeral sessions, deterministic user-config
  isolation, malformed-status failure, path/provenance validation, and strict
  validation of newly reported synthesis pages.
- Moved raw-status and log finalization out of the model prompt and into the
  orchestrator after validation.
- Updated the deterministic synthesis generator to emit evidence scope/count and
  an Evidence Map with per-insight provenance instead of assigning every source
  to every claim.
- Enforced JSON Schema parity across Codex and compatibility backends, moved index
  generation ahead of success finalization, and made auto-commits exclude
  unrelated pre-staged paths.
- Contained strict provenance to existing repository `raw/*.md` files, required
  exact claim-level Evidence Map coverage, and gated checkpoint backfill output.
- Replaced future recurring-checkpoint title generation with topic/decision-shaped
  titles.
- Pinned Codex CLI 0.145.0 in the image, copied the audit helper into standalone
  images, and removed world-writable Codex-home permissions.
- Fixed the linter to ignore TOML/Python double-bracket syntax inside fenced code.
- Updated README, architecture, workflows, and AGENTS documentation.

Existing synthesis pages were intentionally not bulk-rewritten. The audit now
identifies the corpus cleanup queue; an automated rewrite would risk changing
meaning and breaking high-degree links.
